# Community: enabling it and running the SQL

Two things are separate and both are needed: the flag in the app, and the SQL in
the database. **Deploy the code first.** `app/lib/users/search.ts` reads other
users through `public_profiles`; the older code reads `profiles` directly, so
running `profiles-rls.sql` against the old deployment makes people search return
nothing.

## 1. Enable the flag

Set `COMMUNITY_ENABLED` on the deployment (any of `1`, `true`, `yes`, `on`) and
redeploy. It is read per request, so no rebuild is needed to flip it back: with
the flag off there is no footer link, `/community*` and `/api/community*` answer
404 (from middleware, so the status is real) and the bell keeps its old
behaviour.

## 2. Run the SQL, in this order

Run the files, in order, in the Supabase SQL editor. Each one is idempotent and
each has its own rollback.

1. `docs/sql/profiles-rls.sql`
2. `docs/sql/community.sql`
3. `docs/sql/community-patch-1.sql`
4. `docs/sql/comments-deleted-users.sql`

Do **not** also run `supabase/migrations/20261120000000_prompt38_community.sql`
in the same project: it is the same statements, kept in step with the two files
so a migration-based deploy works too. Run the files **or** the migration.

Before running `comments-deleted-users.sql`, compare the live function with the
repo, because production may differ:

```sql
select pg_get_functiondef('public.comments_guard'::regproc);
```

The file header lists every behaviour the replacement preserves.

## 3. Who may do what (generated, not typed)

Generated by running these against the harness database after all four files, so
the table cannot drift from the schema:

```sql
-- functions
select p.proname, pg_get_function_identity_arguments(p.oid),
       has_function_privilege('anon', p.oid, 'execute')          as anon,
       has_function_privilege('authenticated', p.oid, 'execute') as authenticated,
       has_function_privilege('service_role', p.oid, 'execute')  as service_role
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'public' order by 1;
-- tables and views
select c.relname, c.relkind,
       has_table_privilege('anon', c.oid, 'select')          as anon,
       has_table_privilege('authenticated', c.oid, 'select') as authenticated,
       has_table_privilege('service_role', c.oid, 'select')  as service_role
  from pg_class c join pg_namespace n on n.oid = c.relnamespace
 where n.nspname = 'public' and c.relkind in ('r','v') order by 1;
```

Functions:

| function | anon | authenticated | service_role |
| --- | --- | --- | --- |
| `is_staff()` | yes | yes | yes |
| `is_admin()` | yes | yes | yes |
| `comment_link(comments)` | yes | yes | yes |
| `community_feed_page(...)` | yes | yes | yes |
| `community_new_posts(...)` | yes | yes | yes |
| `community_react(text, uuid, smallint)` | **no** | yes | yes |
| `push_allowed(uuid, text)` | yes | yes | yes |
| `comments_guard()` | yes | yes | yes |
| `community_posts_guard()` | yes | yes | yes |
| `anonymise_user_comments(uuid)` | **no** | **no** | yes |

`comments_guard()` and `community_posts_guard()` are trigger functions: EXECUTE is
irrelevant to them because they never run from a client call, and the trigger is
what actually fires. `anonymise_user_comments` is the only function a browser
cannot reach at all.

Tables and views (SELECT at table level; row visibility is RLS, not these grants):

| relation | anon | authenticated | service_role |
| --- | --- | --- | --- |
| `profiles` | yes | yes | yes |
| `public_profiles` (view) | yes | yes | yes |
| `comments` | yes | yes | yes |
| `comment_reactions` | yes | yes | yes |
| `comment_feed` (view) | yes | yes | yes |
| `community_posts` | yes | yes | yes |
| `community_reactions` | yes | yes | yes |
| `community_reports` | yes | yes | yes |
| `community_blocks` | yes | yes | yes |
| `community_moderation_log` | yes | yes | yes |
| `user_notifications` | yes | yes | yes |
| `staff_roles` | **no** | **no** | yes |

A table-level SELECT granted to `anon` does not mean the rows are readable: every
one of these tables has RLS enabled with policies, and `staff_roles` has neither
grants nor policies, so it is unreadable and unwritable from the app entirely.

## 4. Grant the first admin

Roles live only in `public.staff_roles`, which has RLS on, no policies and no
`anon`/`authenticated` grants. It cannot be written from the app, by design:

```sql
insert into public.staff_roles (user_id, role)
select id, 'admin' from auth.users where email = '<owner email>'
on conflict (user_id) do update set role = excluded.role;
```

## 5. Verify

```sql
select relname, relrowsecurity from pg_class
 where relname in ('staff_roles','community_posts','community_reactions',
                   'community_reports','community_blocks','community_moderation_log');

select polname, polcmd from pg_policy where polrelid = 'public.staff_roles'::regclass;  -- no rows
select polname, polcmd from pg_policy where polrelid = 'public.profiles'::regclass;     -- owner-only

select proname, proacl from pg_proc
 where proname in ('community_feed_page') order by proname;
```

## 6. Rollback order

Exact reverse of the run order, because each file depends on the one before it:

1. `docs/sql/comments-deleted-users-rollback.sql`
2. `docs/sql/community-patch-1-rollback.sql`
3. `docs/sql/community-rollback.sql`
4. `docs/sql/profiles-rls-rollback.sql`

The database is left exactly as it was: `profiles` RLS off again, the community
tables and the schedule/trigger additions dropped, `comments_guard` and
`comment_feed` restored to the versions recorded in the rollback file.
