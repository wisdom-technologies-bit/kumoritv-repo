# Community: enabling it and running the SQL

> Phase 6 added the moderation surface. Its handbook - roles, actions, blocks,
> rate limits, the SQL run order, env vars and the screenshots - is
> [community-moderation.md](community-moderation.md). This file stays the
> Phase 1-5 setup guide.

Two things are separate and both are needed: the flag in the app, and the SQL in
the database. **Deploy the code first.** `app/lib/users/search.ts` reads other
users through `public_profiles`; the older code reads `profiles` directly, so
running `profiles-rls.sql` against the old deployment makes people search return
nothing.

## 1. Enable the flag

Set `COMMUNITY_ENABLED` on the deployment (any of `1`, `true`, `yes`, `on`) and
redeploy. It is read per request, so no rebuild is needed to flip it back: with
the flag off there is no footer link, `/community*` and `/api/community*` answer
404 (from middleware, so the status is real) and the bell keeps its old
behaviour.

## 2. Run the SQL, in this order

Run the files, in order, in the Supabase SQL editor. Each one is idempotent and
each has its own rollback.

1. `docs/sql/profiles-rls.sql`
2. `docs/sql/community.sql`
3. `docs/sql/community-patch-1.sql`
4. `docs/sql/comments-deleted-users.sql`
5. `docs/sql/community-comments-arm.sql` (Phase 2: comments in the feed)
6. `docs/sql/community-clips-arm.sql` (Phase 3: shared clips in the feed)
7. `docs/sql/community-phase-4.sql` (Phase 4: `profiles.community_toasts`, the
   announcement columns and the admin write policies)

File 5 may be run before or after the Phase 2 app deploy: it keeps the function
signature and adds one column (`is_adult`) at the end, which the older client
ignores. Until it runs there are simply no comment cards in the feed.

File 6 appends one column (`clip_state`) and one optional argument
(`p_show_adult`) the same way, so it is safe either side of the Phase 3 deploy:
until it runs, a clip post is simply an ordinary text post. Running it before
the app deploy also means the API's `clip_code` insert has its column already.

Do **not** also run `supabase/migrations/20261120000000_prompt38_community.sql`
in the same project: it is the same statements, kept in step with the two files
so a migration-based deploy works too. Run the files **or** the migration.

Before running `comments-deleted-users.sql`, compare the live function with the
repo, because production may differ:

```sql
select pg_get_functiondef('public.comments_guard'::regproc);
```

The file header lists every behaviour the replacement preserves.

## 3. Who may do what (generated, not typed)

Generated by running these against the harness database after all four files, so
the table cannot drift from the schema:

```sql
-- functions
select p.proname, pg_get_function_identity_arguments(p.oid),
       has_function_privilege('anon', p.oid, 'execute')          as anon,
       has_function_privilege('authenticated', p.oid, 'execute') as authenticated,
       has_function_privilege('service_role', p.oid, 'execute')  as service_role
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'public' order by 1;
-- tables and views
select c.relname, c.relkind,
       has_table_privilege('anon', c.oid, 'select')          as anon,
       has_table_privilege('authenticated', c.oid, 'select') as authenticated,
       has_table_privilege('service_role', c.oid, 'select')  as service_role
  from pg_class c join pg_namespace n on n.oid = c.relnamespace
 where n.nspname = 'public' and c.relkind in ('r','v') order by 1;
```

Functions:

| function | anon | authenticated | service_role |
| --- | --- | --- | --- |
| `is_staff()` | yes | yes | yes |
| `is_admin()` | yes | yes | yes |
| `comment_link(comments)` | yes | yes | yes |
| `community_feed_page(...)` | yes | yes | yes |
| `community_new_posts(...)` | yes | yes | yes |
| `community_react(text, uuid, smallint)` | **no** | yes | yes |
| `push_allowed(uuid, text)` | yes | yes | yes |
| `comments_guard()` | yes | yes | yes |
| `community_posts_guard()` | yes | yes | yes |
| `anonymise_user_comments(uuid)` | **no** | **no** | yes |

`comments_guard()` and `community_posts_guard()` are trigger functions: EXECUTE is
irrelevant to them because they never run from a client call, and the trigger is
what actually fires. `anonymise_user_comments` is the only function a browser
cannot reach at all.

Tables and views (SELECT at table level; row visibility is RLS, not these grants):

| relation | anon | authenticated | service_role |
| --- | --- | --- | --- |
| `profiles` | yes | yes | yes |
| `public_profiles` (view) | yes | yes | yes |
| `comments` | yes | yes | yes |
| `comment_reactions` | yes | yes | yes |
| `comment_feed` (view) | yes | yes | yes |
| `community_posts` | yes | yes | yes |
| `community_reactions` | yes | yes | yes |
| `community_reports` | yes | yes | yes |
| `community_blocks` | yes | yes | yes |
| `community_moderation_log` | yes | yes | yes |
| `user_notifications` | yes | yes | yes |
| `staff_roles` | **no** | **no** | yes |

A table-level SELECT granted to `anon` does not mean the rows are readable: every
one of these tables has RLS enabled with policies, and `staff_roles` has neither
grants nor policies, so it is unreadable and unwritable from the app entirely.

## 4. Grant the first admin

Roles live only in `public.staff_roles`, which has RLS on, no policies and no
`anon`/`authenticated` grants. It cannot be written from the app, by design:

```sql
insert into public.staff_roles (user_id, role)
select id, 'admin' from auth.users where email = '<owner email>'
on conflict (user_id) do update set role = excluded.role;
```

## 7. Adult content in the community feed

Comments of an anime with `anime.is_adult = true` are hidden from
`community_feed_page` unless the caller passes `p_show_adult = true`. The app
passes the value it already uses everywhere else: the signed-in profile's
`show_adult`, else the `is_adult_content_enabled` cookie, and `false` for a
guest.

This is a **display preference, not an authorization boundary and not age
verification**. A signed-in viewer can turn it on in settings, `/media/<id>` is
reachable either way, and the RPC is granted to `anon`. It is the same switch
the rest of the site has always honoured; nothing here is a legal or safety
gate, and it must not be described as one.

The card shows an "18+" chip when a row is returned with `is_adult = true`, so a
viewer who has the setting on can still tell what they are reading in a mixed
feed.

## 8. Sharing clips (Phase 3)

A post can carry one of your clips instead of, or as well as, text. The clip
travels as `community_posts.clip_code` (the 7-character clip code), never as a
URL: `link_url` keeps its Phase 1 meaning and the posts API accepts exactly one
of the two. A pasted `https://kumoritv.top/clip/<code>` becomes a code before it
is stored.

What the four surfaces do:

- **Composer.** A clip chip opens a picker with two tabs, *My recent clips*
  (`GET /api/clips/mine`) and *Paste clip URL*. Choosing a clip attaches a
  preview card with the anime, episode, range and length; Remove takes it back
  off. Pasting a clip link into the post box attaches it and strips the link
  from the text, so the post says the words and the card says the clip. A post
  may be a clip with no text.
- **Feed card.** `community_feed_page` returns `clip_state` and the card draws
  that and nothing else: `live` is a poster, the title and
  `Anime · E12 · 1:02-1:17 · 15s`; `removed` is "This clip was removed"; a text
  post stays a text post.
- **Post page.** `/community/post/<id>` resolves the clip through the same
  check and shows the same card, including in `generateMetadata`.
- **Feed filter.** A fifth chip, *Clips*, asks the RPC for `p_kind = 'clips'`.
  Five chips do not fit a 360px phone with the full labels, so the phone bar
  uses short ones (the announcement chip reads *News* there).

`app/lib/community/clip-post.ts` holds the rule as one pure function
(`buildClipCard`, `clipCardFor`, `clipPostHeadline`), so the feed, the post page
and their tests cannot drift apart.

### The adult rule for clips

A clip whose anime is adult (AniList `isAdult`, which covers the Hentai genre)
is treated as follows, and every part of it is enforced before the data leaves
the server:

- The post card is labelled **"Adult content 18+"**.
- The thumbnail, the title, the anime name, the range and the clip link are all
  withheld: the viewer with the setting off sees only the label and
  **"Turn on adult content in settings to view"**.
- `community_feed_page` returns `clip_state = 'hidden_adult'` and NULLs
  `clip_code`, `clip_start`, `clip_end`, `anime_id`, `anime_title`,
  `anime_cover`, `episode_number` and `title` for that row, so there is nothing
  in the response to leak.
- The composer picker masks the same rows, the composer preview is masked
  server-side by `GET /api/clips/<code>` (`{isAdult: true, hidden: true}`), and
  `community_new_posts` returns `has_clip = true` with a generic "Shared a clip"
  and no code or anime until the caller's setting is on.

This is the site's existing adult-content preference, **not age verification**
and not an authorization boundary: a signed-in viewer can turn it on in
settings, the clip page is reachable either way, and the RPC is granted to
`anon`. It must not be described as a safety or legal gate.

## 10. Phase 4: the new-post bar

A small bar appears at the top of the page when someone posts in Community.
Nothing else changed: it polls, it never opens a websocket, and with
`COMMUNITY_ENABLED` off it does not exist.

### How it works, in one paragraph

`GET /api/community/latest?after=<cursor>&limit=5` returns the newest public
items created after the cursor: posts with status `visible`, and announcements
that are published and not expired. The toast polls it every 30 s with
`If-None-Match`, so an unchanged feed costs a `304` with no body. The response
carries `Cache-Control: public, s-maxage=5, stale-while-revalidate=10` and the
endpoint keeps a 10 s in-memory cache per instance, because the payload is
identical for every viewer. A per-IP limit of 60 requests a minute answers a
scraper with `429` and `Retry-After`. Worst case, an edge cache delays a new
post by 15 s; it can never hide it, because the next poll's cursor is still
behind the post.

**Where "new" starts.** The response ALWAYS carries `cursor`, even when `items`
is empty: it is the newest `created_at` among public items, or the server's
`now` minus 10 s when the community has nothing public yet. The client seeds its
cursor from that field on the first poll and never from the max of the items it
received. That distinction is the whole fix in Part A below: seeding from an
empty item list leaves the client with no starting point, so the next poll is
treated as a first load again and the first real post is swallowed. The `after`
filter is **inclusive** (`>=`) and the client de-duplicates by id, so a post
written in the same millisecond as the cursor cannot fall between two polls.
Timestamps are compared as numbers (`Date.parse`), never as strings, so `Z` and
`+00:00`, microseconds and milliseconds all compare correctly.

### The API contract

```
GET /api/community/latest?after=2026-11-17T09:00:00.000Z&limit=5
```

```json
{
  "items": [
    {
      "id": "…",
      "kind": "post",
      "authorId": "…",
      "authorName": "Ada",
      "authorAvatar": "https://…",
      "text": "first 140 characters, Markdown stripped",
      "hasClip": true,
      "clipThumb": "https://… or null",
      "adult": false,
      "href": "/community/post/…",
      "createdAt": "2026-11-17T09:04:11.000Z"
    }
  ],
  "cursor": "2026-11-17T09:04:11.000Z"
}
```

* `cursor` is the newest `created_at` in the response; pass it back as `after`.
* Responses carry `ETag`; send it back as `If-None-Match` and an unchanged feed is
  `304` with no body.
* With the flag off: `404`, and the route never touches the database.
* Hidden, removed and adult-gated rows never appear. A post marked `[deleted]`
  keeps the `[deleted]` author name; a spoiler post's text is the word
  "Spoiler"; adult clip posts are reduced to `{id, kind, adult: true, href,
  createdAt}` with the text "New 18+ clip" and no thumbnail, so the cached
  payload is byte-identical for everyone and nothing adult is ever leaked to a
  reader who did not ask for it.

### Turning the bar off

* For one reader: Settings → Notifications → "New post notifications". Stored in
  `profiles.community_toasts` (default on) and mirrored to `localStorage` so
  guests keep their choice too. The bar reads the setting at poll time, so the
  switch takes effect without a reload.
* For everyone: set `COMMUNITY_TOASTS=off` (or `0`/`false`/`no`) and redeploy.
  The community itself keeps working.
* Tuning, all optional: `COMMUNITY_POLL_SECONDS` (30), `COMMUNITY_TOAST_SECONDS`
  (5), `COMMUNITY_TOAST_MIN_GAP_SECONDS` (10). Unset means the default.

### `?toastdebug=1` (the owner's on-phone diagnostic)

Add `?toastdebug=1` to any page with `COMMUNITY_ENABLED=1` and a small chip sits
bottom-left. It is read from the URL on every render and never stored; without
the parameter nothing renders. It shows:

* `enabled on/off` - the flag reached the browser;
* `setting on/off` - your per-user switch;
* `path suppressed` - you are on `/community`, where the pill replaces the bar;
* which account the browser thinks it is (`guest`, or the first 8 characters of
  the user id) - this is what tells two accounts apart on one phone;
* `poll HH:MM:SS · 200/304/429/error · items N`;
* the current cursor;
* `no toast: <reason> · <path>` with one of `seeded`, `shown`, `path`,
  `fullscreen`, `preroll`, `typing`, `setting`, `own item`, `throttled`,
  `visible`, `deferred`, `none new`;
* a **Show a sample toast** button that renders a fake item through the real
  toast component, so the visual part can be checked in one tap.

### How to test the toast in 2 minutes

1. Phone A: open the home page signed in, with `?toastdebug=1` if you want the
   chip. Leave it there.
2. Phone B (or a private window on another account): post in Community.
3. Within 45 s phone A shows "Ada posted" at the top. The chip's `poll` line
   advances every 30 s; the reason after a successful toast reads `shown`.
4. Post from phone A's own account: no toast, and the chip says `own item`.
5. Open `/community` on phone A: no toast there by design; the "N new posts"
   pill counts instead, and the chip says `path suppressed`.

If nothing appears, the chip's reason names the cause: `setting` (the switch is
off), `guest` next to `enabled on` (the browser has no session), `none new`
(the poll is not reaching a server with the post), `429` (rate limited),
`error` (the request failed).

### When the bar stays quiet

No toast for your own posts, on `/community` (there you get the "N new posts"
pill instead), in fullscreen, while a pre-roll ad is pending on the watch page,
while you are typing in a field, or when you asked for it to be off. At most one
toast every 10 s; anything newer is collapsed into the next one ("Ada and 2
others posted"). It is a `role="status"` live region, it never takes focus, and
hovering or focusing it pauses its 5 s timer.

### Why polling and not Realtime

Polling with an ETag costs one conditional request per reader per 30 s, and a
`304` is a few hundred bytes. Supabase Realtime would be instant, but every open
tab holds a connection: the Free plan allows 200 concurrent connections and Pro
allows 500. On a release night with a few thousand readers, Realtime would be
the larger bill and the larger failure mode, and this feature does not need
instant. If the numbers ever justify it, the swap point is one function: the
polling loop in `app/components/CommunityToast/` - replace its `setInterval` and
`fetch` with a channel subscription that calls the same `nextToast` state
machine. Nothing else in the app would change.

## 11. Announcement previews (everything except the announcement itself)

An announcement body is Markdown. Until this change, every surface outside the
announcement's own page printed the raw source: `# Service Update`,
`**bold**` and `https://...` appeared literally, in one paragraph with no
clamp, so a long body pushed the feed card off the screen.

There is now one renderer with two variants, in `app/lib/community/markdown.tsx`:

* `variant="full"` - the announcement page and the admin composer preview.
  Headings, lists, quotes, code and images all render.
* `variant="preview"` - every feed card, rail item, index excerpt and bell
  notification. Same safe rules (no raw HTML anywhere, no `rehype-raw`, links
  limited to `https:`, `http:`, `mailto:`), but the block structure is flattened
  for a card: headings become bold paragraphs, lists become compact lines,
  blockquotes are inlined, images/rules/code blocks are dropped, and links stay
  clickable while never nesting an anchor inside the card's own link.

The preview cuts the SOURCE, not the DOM: `preparePreview` keeps the first
~320 characters and at most 6 lines at a word boundary, then repairs the cut
(an unclosed `[label](url)` keeps its label, an unclosed `**` is dropped, a bare
URL that was cut is removed) and only then renders. Truncation therefore can
never leave a half-parsed tag. The rendered box is clamped in CSS
(`-webkit-line-clamp: 4` on phones, 5 from 768 px) and "Read more" appears
exactly when the source was cut.

| Surface | File | Before | After |
| --- | --- | --- | --- |
| Feed card | `app/community/components/AnnouncementCard.tsx` | one unclamped `<p>` of raw Markdown | preview + clamp + "Read more" |
| Right rail "Latest announcements" | `app/community/components/rails.tsx` | raw body, unbounded | title + date + 2 clamped plain lines |
| `/community/announcements` index | `app/community/announcements/AnnouncementList.tsx` | raw body text | preview + clamp + "Read more" |
| Bell dropdown | `app/layout/header/components/Notifications/index.tsx` | excerpt built from raw source, could show `**` | `plainSnippet` of the rendered-safe text |
| OG / meta description | `app/community/announcements/[id]/page.tsx` | already plain text | unchanged (verified plain) |

## 12. Phase 4: writing announcements (Markdown)

Announcements are written from the site now, not in the Supabase Table Editor.
The table keeps its shape apart from three columns (`updated_at`,
`created_by`, `idempotency_key`), and `docs/sql/community-phase-4.sql` adds them
before the code needs them.

### Step by step, for the owner

1. Sign in with the admin account (the id in `public.staff_roles`).
2. Open `/community/announcements` and press **Write announcement**. That button
   only exists in an admin's HTML, and the page itself is a 404 for everyone else.
3. **Title**: what the card and the bell show. Maximum 120 characters.
4. **Body**: Markdown, maximum 5,000 characters. The toolbar inserts Heading,
   Bold, Italic, Link, List and Quote at the cursor, and the Preview pane is the
   real renderer, so what you see is what publishes.
5. **Image URL** and **"Read more" link**: optional, `https://` only.
6. **Expiry**: optional. Empty means it never expires. You pick it in your own
   timezone; it is stored in UTC.
7. **Send push notification**: on by default. Turn it off to publish quietly: the
   row is stamped so the cron skips it, and nothing is sent later either.
8. Press **Publish**, check the confirm step (it shows the exact preview and says
   whether a push goes out), then **Publish now**.

A double click cannot create two announcements: the browser sends one
idempotency key per compose attempt and a unique index rejects the second insert.
Editing an already pushed announcement never re-sends its push. Below the form
every announcement is listed with its status and three actions: Edit, Expire
now, Delete.

### The Markdown you can use

Headings `#` to `###`, paragraphs and line breaks, **bold**, *italic*, ordered
and unordered lists, blockquotes, horizontal rules, inline code, links and bare
autolinks. That is the whole subset, on purpose:

* raw HTML is never rendered (`<script>`, `<img onerror>` and friends are
  dropped: there is no `rehype-raw` in the tree),
* links are only `https:`, `http:` and `mailto:`; `javascript:` and `data:` are
  removed, and external links open in a new tab with
  `rel="noopener noreferrer nofollow ugc"`,
* images in the body are not rendered. Use the Image URL field,
* a body `#` becomes an `h2` on the page, because the title is the only `h1`.

The sample that has to keep working, exactly as typed:

```markdown
# Service Update: KumoriTV Is Back Online!

We are pleased to announce that **KumoriTV is fully accessible again!**

The temporary service disruption has been resolved, and our website is back up and running.

We sincerely apologise for the inconvenience ... Thank you for staying with us.

**We're back. Happy watching!**

*The KumoriTV Team*
https://kumoritv.top
```

The plain-text projection (Markdown stripped, 140 characters cut at a word
boundary) is what the bell preview, the `<meta>` description, Open Graph and the
push body carry. Old plain-text announcements still render: plain text is valid
Markdown.

### The admin API

All three routes need a real session and `is_admin()`, allow 10 writes a minute
per admin, validate every field server-side and reject unknown fields. They write
with the caller's own session, so RLS applies underneath.

| Method | Route | Body |
| --- | --- | --- |
| POST | `/api/community/admin/announcements` | `{title, body, image, url, expiresAt, sendPush, idempotencyKey}` |
| PATCH | `/api/community/admin/announcements/[id]` | the same fields; `sendPush` is ignored |
| DELETE | `/api/community/admin/announcements/[id]` | - |

Answers are `{ok: true, id}` or `{error, message}`, with status `400` validation
(with `field`), `401` no session, `404` not an admin or not found (deliberately
indistinguishable), `429` rate limited with `Retry-After`, `500` write failed and
never a database message. No service role is used in this phase: RLS expresses
every rule, including "an edit never re-sends".

The audit line goes to the server log as
`[community][audit] <action> announcement=<id> admin=<uid>`, not into
`community_moderation_log`: that table only accepts
`hide/unhide/remove/restore/role_change` and has no insert grant for browser
roles. Widening its check constraint for four new verbs was not worth touching a
table Phase 2 already relies on.

### Known limits

* `/community/announcements` is indexable and in the sitemap only while
  `COMMUNITY_ENABLED` is on.
* "Load more" is keyset pagination on `created_at`; two announcements published in
  the same millisecond could order either way.
* "Expire now" sets the expiry two seconds ahead, because the validator only
  accepts a future instant; the row leaves the lists immediately after.
* The composer keeps one draft per browser, not per announcement: editing an
  existing announcement does not overwrite a draft.
* Real push delivery still depends on OneSignal and each reader's preference. The
  tests use a stand-in transport, so they prove the call, not the delivery.
